# I7 pipeline source contracts and remaining activation

The dedicated APP staging workflow is `.github/workflows/staging-deploy.yml`. It listens only to pushes on `develop`; pull requests, tags, manual dispatches, schedules, `main` and production are absent by construction. The deployment job runs only when the repository/environment configuration variable `APP_CLOUD_DEPLOYMENT_ENABLED` is exactly `true`, references the protected `staging` environment, and is the only job with `id-token: write`. AWS credentials are obtained through OIDC using the reviewed `APP_CLOUD_DEPLOYMENT_ROLE_ARN` variable; no long-lived credential or secret value is stored in the workflow.

Before enabling the gate, configure these reviewed, non-secret repository/environment variables: `APP_CLOUD_DEPLOYMENT_ENABLED`, `APP_CLOUD_DEPLOYMENT_ROLE_ARN`, `APP_RELEASE_INPUT_PATH`, `APP_PLATFORM_INPUTS_PATH`, `APP_CLOUD_WINDOW_EVIDENCE_PATH`, `APP_TERRAFORM_VARIABLES_PATH`, `APP_TERRAFORM_VARIABLES_SHA256`, and `APP_DEPLOYER_IMAGE_DIGEST`. The four path variables must resolve to committed or otherwise reviewed files available after checkout. The workflow fails before AWS configuration when any required variable or file is absent; keep `APP_CLOUD_DEPLOYMENT_ENABLED` unset or different from `true` until the external IAM role, environment branch policy, release inputs and cloud-window evidence have been reviewed.

The Terraform variables file must be a reviewed JSON object containing configuration/references, never credential values. `APP_TERRAFORM_VARIABLES_SHA256` is the independently reviewed lowercase 64-character SHA-256 of its exact bytes; the workflow does not calculate a replacement review digest. `APP_DEPLOYER_IMAGE_DIGEST` is the reviewed executor digest in `sha256:<64 lowercase hex>` format, distinct from the application's runtime image digest. The release input JSON must include matching `terraformVariablesSha256` and `deployerImageDigest` fields. Packaging preserves these fields in the manifest. The workflow calls `start-deploy.ps1 -DryRun` before OIDC, rejecting missing, malformed or mismatched bindings without AWS access.

The launcher requires `-TerraformVariablesFile`, `-ExpectedTerraformVariablesSha256`, and `-DeployerImageDigest` for both dry-run and live invocation. It uploads the exact variables file under `releases/app/<environment>/config/<sourceCommit>.tfvars.json` in the same artifact bucket. It requires a nonempty, non-`null` S3 VersionId and passes `TFVARS_OBJECT_KEY`, `TFVARS_VERSION_ID`, `EXPECTED_TFVARS_SHA256`, and `DEPLOYER_IMAGE_DIGEST` alongside the existing nine source/manifest overrides. The closed override list matches the platform executor contract; no commands, secret values, backend paths or arbitrary overrides are forwarded. Staging promotion evidence and its local receipt retain the tfvars object key/version/hash and executor digest, without copying configuration contents.

The staging adapter paths now match the platform-owned inline buildspec observed through read-only CodeBuild metadata on 2026-09-18: `/tmp/oficina/application_staging.tfvars.json`, `application/staging.tfstate`, and its derived `application/staging.tfstate.tflock`, in `us-east-1`. The old `app` staging paths, other environments, mismatched lock keys, alternate regions and traversal paths are rejected. The artifact prefix remains `releases/app/staging`; source-object identity and Terraform state identity are separate contracts. Production retains its existing `app/production.tfstate` and `/tmp/oficina/app_production.tfvars.json` contract until a separate executor review.

This path alignment does not activate the APP executor: valid staging inputs with `-ApplyReviewedPlan`, with no mode switch, or with both `-ApplyReviewedPlan -DryRun` still fail with `APP_DEPLOYMENT_DISABLED` before any Terraform operation. A dry-run alone returns `INPUTS_VALIDATED_DEPLOYMENT_DISABLED`. The observed inline buildspec supplies `-ApplyReviewedPlan`, so it will reach that explicit disabled guard after input validation instead of failing on the stale path names. Migration/rollout orchestration, shared lock, cloud-window guards and release promotion still require separately reviewed activation. Providing all launcher inputs or passing the dry-run does not prove deployment success. No production workflow or automatic apply is added. Offline `release-guards-contract.ps1` exercises the exact staging paths and asserts the disabled error, with AWS, Terraform and kubectl commands forbidden.

The live CodeBuild source location also points to `releases/application/staging/bundle.zip`, whereas this repository's reviewed source contract is `releases/app/staging/bundle.zip`. Its automatic source download can fail before the inline buildspec runs: the source VersionId belongs to the canonical `app` object, not the configured `application` object. The launcher deliberately rejects `releases/application/staging`; changing its prefix or adding an arbitrary source-location override would hide the platform mismatch. Correct the platform-owned project source location through its separately reviewed infrastructure change before launching. The project has no preset environment variables, so every required override must come from this verified launcher.

The workflow packages the exact `GITHUB_SHA` through `scripts/offline-release-handoff.ps1`, which binds `source.zip` and `release-manifest.json` to that source commit, then invokes `scripts/start-deploy.ps1` with the fixed reviewed values `oficina-phase3-artifacts-16225b7358`, `releases/app/staging`, and `oficina-phase3-oficina-app-staging-deploy`. The launcher verifies hashes, branch context, cloud-window evidence and staging inputs before upload; successful staging promotion evidence is retained as a workflow artifact. This workflow does not provision infrastructure, run Terraform, or provide a production path.

The source contract maps a push to `develop` to the existing opt-in staging job. That job is skipped unless `vars.APP_CLOUD_DEPLOYMENT_ENABLED` is exactly `true`; it is the only APP job that requests AWS OIDC and it is constrained to the protected `staging` environment. There is no production or `main` deployment job: PRs, `pull_request_target`, tags, manual dispatch and other branches cannot pass `check-workflow-context.ps1`. CI verification identities remain read-only. APP's GHCR publishing is push-only and its Kind job is explicitly a local smoke test, not an AWS release.

`package-source.ps1` archives the reviewed Git tree with a fixed timestamp. Equal trees at different merge commits produce identical SHA-256 bytes; changed content requires staging again. Runtime image/JAR digest, contract version and migration version are separate required release-manifest fields. `start-deploy.ps1 -DryRun` validates artifact/manifest hashes, exact repository/environment executor/prefix, branch context, an open fresh cloud window and production's exact staged-source digest. Its dry-run result is explicitly `INPUTS_VALIDATED_DEPLOYMENT_DISABLED`; the offline and dry-run paths remain disabled, while the opt-in staging workflow may invoke the reviewed live launcher after all activation prerequisites pass. `deploy.ps1 -ApplyReviewedPlan` remains disabled. These checks are not a signed promotion attestation and cannot authorize a cloud deployment by themselves.

For a deterministic local APP handoff, run `pwsh -File scripts/offline-release-handoff.ps1 -SourceCommit REVIEWED_COMMIT -ReleaseInputFile review/release-input.json -PlatformInputsFile review/platform.json -OutputDirectory review/handoff`. The command packages the reviewed tree, adds and verifies the archive digest in `release-manifest.json`, invokes the local renderer, hashes the rendered files, and writes `release-receipt.json` with `success: false` and `status: INPUTS_VALIDATED_DEPLOYMENT_DISABLED`. It performs no AWS, OIDC, CodeBuild, Terraform or kubectl operation and refuses a non-empty output directory.

The vendored cloud-window and lock scripts preserve the platform protocol: numeric allowance evidence or explicitly approved study-staging billing acknowledgment; fresh timestamps and closed-window rejection; conditional creation of `deployment-locks/shared-foundation.json` in the existing state bucket; ownership-only release and no stealing. Tests use the offline lock implementation and never acquire a real lock. Production can never use the study-staging billing acknowledgment.

`export-outputs.ps1` exports only the committed output allowlist and refuses sensitive allowlisted fields. APP's schema/bootstrap references are distinct environment/account Secrets Manager ARNs (no values); schema/view versions remain V8/V5/V7. FUN public JWK output rejects private parameters. Unknown password/state fields are dropped. Exported documents do not prove SQL privileges, key initialization or deployment success.

## External protections and activation prerequisites

Configure actual PR-only `main`/`develop` protections, required CI checks/review, restricted bypass, staging's develop-only environment policy and production's main-only policy before requesting deployment identity. Record repository identity/visibility, exact immutable OIDC subject, protection/ruleset IDs, required status check names, environment branch policies and reviewer settings as dated evidence. Workflow YAML cannot establish those controls and this change does not modify them.

APP now has an offline-tested [migration/first-writer and compatible rollback adapter](runbooks/first-writer-cutover.md), consuming the reviewed K8S renderer inputs. It is not connected to the disabled cloud launchers. Its standalone [role/credential bootstrap adapter](runbooks/database-bootstrap.md) has local PostgreSQL authorization tests; reviewed image/I6 Job wiring, RDS capability verification, actual versioned secrets and v2 receipt consumption remain prerequisites. The merged [FUN gateway handoff](https://github.com/rafaelxvr/Tech-challenge-15SOAT-functions/pull/6) and [K8S gateway ownership change](https://github.com/rafaelxvr/Tech-challenge-15SOAT-k8s-infra/pull/5) make the live staging base API K8S-owned (`qcm8l43flb`, `$default`) with public `GET /health` and `POST /api/auth/login`; no protected route or FUN runtime is claimed. Remaining runtime-input, secret and receipt checks are: verify the staged FUN artifact bytes against both recorded digests; provide the customer/staff key IDs, public JWK map, invocation forecast and pinned New Relic layer ARNs; create and review the `customer_signing_key`, `authorizer_trust` and `rds_ca_certificate` secret slots; then produce the FUN plan/apply output receipt and return the four-field `gateway_handoff` to K8S. The launchers remain disabled, and no eight-run R4 result is claimed. Do not substitute `promotedFromStaging=true` for that evidence.

The dependency order remains human state/OIDC bootstrap → foundation/private executors → platform/RDS → APP schema/roles/views → functions → stable Service/target binding and authorized APP routes/rollout → monitoring bindings. Actual cloud execution and production changes are outside this source task.

Local checks: `tests/start-deploy-contract.ps1`, `tests/staging-deploy-workflow-contract.ps1`, `tests/source-package-contract.ps1`, `tests/workflow-context-contract.ps1`, `tests/cloud-window-tests.ps1`, `tests/release-guards-contract.ps1` and `tests/pipeline-contract.ps1`; the pipeline includes the launcher contract in an isolated offline PowerShell process. FUN also runs `tests/verify-infrastructure.ps1`. Each repository owns its copied guard snapshot; security fixes must be propagated with its tests.

Lock release checks the owner and observed ETag from the same HEAD, then sends `DeleteObject --if-match` with that exact ETag. A replacement owner changes the lock payload; S3 rejects the stale conditional delete. Missing/wildcard ETags and every delete failure stop release without retrying unconditionally. No specific object version is permanently deleted. The executor AWS CLI must support [S3 DeleteObject If-Match](https://docs.aws.amazon.com/cli/latest/reference/s3api/delete-object.html); an older CLI fails closed and must be updated in its separate reviewed image release. Offline lock mutations use a shared named mutex around owner comparison/deletion. `tests/deployment-lock-race-contract.ps1` deterministically replaces owner A with B between HEAD and DELETE and proves B survives; the old implementation fails this test. AWS calls in this proof are mocked.
