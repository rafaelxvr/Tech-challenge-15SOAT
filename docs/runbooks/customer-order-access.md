# Customer order access rollout

1. Require new login after deploying the separated JWT trust and customer authorization changes. Staff continue with `POST /api/auth/login`. Customers complete CPF + email code through the gateway to receive the customer access JWT (15 minutes, no refresh). A staff login or legacy `CLIENTE` staff role does not substitute for a customer token.
2. Use the actual `numero` returned when staff creates the order. `GET /api/ordens-servico/{numero}/acompanhamento` requires `principal_type=customer`, `orders:read:self` and the order's owning customer UUID. `POST /api/ordens-servico/{numero}/orcamento/decisao` requires customer identity and `orders:decide:self`. Missing or non-owned orders return the same 404. Staff continue using staff routes.
3. Set the Postman environment's `customerToken` to the newly issued customer JWT for that order's customer. Keep `bearerToken` for staff operations. The canonical decision body is `{"decisao":"APROVADO","observacao":"Autorizo este orçamento"}` or `{"decisao":"RECUSADO"}`. No document/UUID belongs in this canonical body. The estimate response contains descriptions, quantities, prices and status history; customer names, documents, vehicle plates, contacts, internal actors and free-form internal notes are excluded.
4. Migrate callers from `/aprovar` and `/orcamento/notificacao` to `/orcamento/decisao`. Compatibility aliases require the same customer token, exact decision scope, ownership and domain transition; their legacy `documentoCliente` only confirms the already authenticated owner. Approval records `CUSTOMER` and its UUID, starts execution and deducts stock once. Refusal returns to diagnosis without stock movement. Duplicate decisions cannot bypass the aggregate guard. A concurrent loser returns 409; fetch the current state before deciding what to do next.
5. Remove callers and deployment injection of `MAIL_STATUS_TOKEN` during the separately owned deployment rollout. The application no longer consumes this setting. `/api/ordens-servico/email/atualizar-status` always returns 404, including with the former token; its controller mapping, DTO and service mutation are removed. Emails are notifications that direct users to authenticated operations. This APP change does not modify gateway, K8S, Terraform or cloud secrets. Deployment owners must remove those legacy inputs/routes there.

Only `POST /api/auth/login` and `GET /api/actuator/health` are anonymous APP operations. Swagger and OpenAPI require staff authentication; other actuator endpoints keep staff restrictions. Customer auth endpoints are implemented by the separate gateway/function contract, not wildcard APP auth mappings.

Full application MockMvc tests set `/api` as servlet context. Controller-only tests intentionally omit `/api`; route matchers operate on application paths. Runtime test keys are generated fixtures, never deployment secrets. PostgreSQL tests use persisted customer/order fixtures and generated order numbers; they verify committed ownership, customer actor, stock, replay and concurrent decision behavior.
