# APP-owned database role and credential bootstrap

Status: source adapter with real disposable PostgreSQL 16 tests. No AWS secrets, SQL users, cloud resources or deployment were created by this change. `BootstrapMain` is a separate Java entrypoint, not a Spring bean/startup hook. It is not wired into the disabled cloud release launcher or the existing Flyway-only I6 Job.

## Reviewed inputs and external injection

An authorized secret-provisioning process must first create four independent versioned Secrets Manager credentials in the target account/environment. This adapter **reads only** five exact ARN/version pairs: the RDS-managed master and the four runtime/migration references. It never creates, updates or prints secrets. Runtime consumers must never receive the master reference or credential.

The reviewed JSON consumed by `com.oficina.bootstrap.BootstrapMain` has `schemaVersion: 1`, `environment: staging|production`, a 40-character `sourceCommit`, DNS-only `databaseHost`, `caSha256`, `master: {arn, versionId}` and `roles` with exactly `migration`, `app`, `auth`, `notification`, each `{arn, versionId}`. Master ARN must be the explicit same-account us-east-1 `rds!db-...` reference. Runtime ARNs must be `arn:aws:secretsmanager:us-east-1:ACCOUNT:secret:oficina/ENVIRONMENT/ROLE-SUFFIX`, with the real six-character Secrets Manager suffix. Version IDs are immutable 32–64-character identifiers; stage aliases such as `AWSCURRENT` are rejected. No password appears in this input file.

Each externally provisioned runtime secret contains JSON `username` and `password`. Names are exact: `oficina_ENVIRONMENT_migration`, `oficina_ENVIRONMENT_app`, `oficina_ENVIRONMENT_auth`, `oficina_ENVIRONMENT_notification`. Runtime passwords must have at least 32 characters; the managed master credential has its provider-defined username and at least 16 password characters. Use independently generated values and disable SDK/JDBC wire or parameter logging in the reviewed executor. Passwords are passed through in-memory JDBC parameters, never command arguments, generated files, review JSON or receipts. Provider/SQL errors are reduced to a fixed failure code at the entrypoint; do not enable heap dumps or publish process memory.

The master JSON is resolved only through `GetSecretValue(SecretId=reviewed ARN, VersionId=reviewed version)`. The response ARN/version must match. Database host/database/TLS settings come from the reviewed input, not arbitrary secret fields. Every connection uses database `oficina`, port 5432, `sslmode=verify-full`, a separately supplied CA file whose SHA-256 must match, and bounded connection/socket timeouts.

## Administrative sequence

1. After I6 has drained every old writer, obtain the approved bootstrap document/checksum, matching source/runtime artifact, pinned CA and environment deployment lock. Inventory the dedicated APP database. Unrecognized non-extension relations/functions in public schema cause rejection; unsupported ownership/membership drift needs a separate review.
2. The master connection creates missing restricted LOGIN roles and reconciles passwords from the exact reviewed secret versions. All four roles are NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, NOBYPASSRLS and NOINHERIT. Existing unsafe attributes, inherited memberships/database ownership or runtime schema ownership cause rejection. PostgreSQL 16 grants the administrative login membership in the migration role for ownership reconciliation; none of the three runtime logins receives that membership.
3. Bootstrap revokes PUBLIC database/schema privileges, preinstalls the trusted `uuid-ossp` extension with the administrative login and transfers only reviewed APP schema objects to migration ownership. Flyway runs V1–V8 as the migration login with clean/baseline/out-of-order disabled. Historical migration files remain unchanged. Preparation and grants each use a transaction/advisory lock; the enclosing deployment lock must span the complete prepare/migrate/grant/proof sequence.
4. Migration owner grants APP SELECT/INSERT/UPDATE/DELETE only on the twelve approved business tables and USAGE/SELECT on `ordens_servico_numero_seq`. Auth receives SELECT only on `auth_cliente_snapshot`; notification receives SELECT only on `notificacao_destinatario_snapshot`. All runtime logins have CONNECT and schema USAGE, no TEMP, schema CREATE or migration-history access. PUBLIC grants on APP tables/views/sequence/types/trigger function and unsafe global/schema default grants are revoked. Future objects receive no automatic runtime grants. Trusted extension functions retain their extension-defined privileges; bootstrap does not claim to audit arbitrary extensions.
5. The known development `admin@oficina.com` seed is disabled idempotently before runtime proof. Provision a separately reviewed operational staff identity; this adapter does not establish its password or publish it. Runtime connections prove their permitted read plus DDL/TEMP/history denials, and both lookup roles prove SELECT/DELETE denial on every base table and denial on the other view. Only after all checks succeed is a new reference-only receipt written; a pre-existing receipt path is rejected.

Roles and grants are idempotent for the reviewed schema and versions. This does not mean credential rotation is automatic: changing a VersionId/password requires coordinated review of consumers. A preparation/migration/grant failure leaves no successful receipt and must block I6 writer startup. Flyway may have committed completed migrations before a later failure; do not reverse V5–V8 or restore an incompatible writer. Reconcile the exact state and use the compatible recovery process.

## Source packaging and staging prerequisites

Build the separate Java classpath from the same reviewed source with Java 17: `./mvnw -B -DskipTests compile dependency:copy-dependencies -DoutputDirectory=target/bootstrap-libs`. The future immutable executor image must include `target/classes` (including the exact Flyway resources) and those locked dependency versions. This command builds local source only.

Inside the separately authorized private executor, the interface is `java -cp 'target/classes:target/bootstrap-libs/*' com.oficina.bootstrap.BootstrapMain REVIEW_JSON REVIEW_SHA256 PINNED_CA_FILE NEW_RECEIPT_PATH` (use `;` as the classpath separator on Windows). Arguments carry only references/paths/hashes. The SDK obtains credentials through the executor's reviewed workload identity; fixed AWS credentials are not part of this source contract. IAM must allow GetSecretValue on those exact five secret ARNs and necessary decrypt only for their reviewed customer-managed KMS keys, with no secret creation/update permission. Keep master read/decrypt rights entirely out of APP/FUN runtime roles.

Before staging, review the image digest and source provenance; supply actual immutable secret versions, RDS TLS CA hash, database endpoint and administrative role authority; ensure a private network path to RDS/Secrets Manager/KMS, appropriate namespace service account/IRSA and secret-free logging. Review the administrative login's PostgreSQL/RDS-specific CREATE ROLE, extension and ownership-transfer capabilities. The tests deliberately use a non-superuser PostgreSQL administrator, but do not prove RDS-managed service behavior. Confirm role/schema/credential readiness with the private staged run before binding public routes.

The existing I6 Job currently invokes a Flyway CLI with its migration credential only. Replacing/wrapping it with this reviewed bootstrap entrypoint, binding the five references to the reviewed release, retaining its receipt and making successful bootstrap proof part of the rollout gate are explicit activation work. Do not run bootstrap before the first-writer drain, or pretend this standalone entrypoint is already integrated into the Job.

## Receipt version and validation

The [v2 receipt contract](../../contracts/bootstrap-receipt.v2.json) publishes V8/V5/V7 plus **four runtime ARN and immutable VersionId pairs** and source/environment metadata. It omits master reference, usernames, password values, endpoint, SQL and provider details. The previous DB v1 exact-field receipt validator and APP Terraform-output exporter do not understand the VersionId fields; do not silently drop them or label this as v1. Add reviewed v2 consumer/publisher support before pipeline activation.

Run `./mvnw -B -Dtest=DatabaseRolesTest,BootstrapContractTest test` (quote the `-Dtest=...` argument in PowerShell), then full `./mvnw -B verify`. Tests generate credentials locally and use PostgreSQL 16 Testcontainers; all AWS clients are mocked. They cover empty bootstrap, V4 upgrade, reruns, APP CRUD/sequence use, lookup views, forbidden base-table/DDL/history/other-view access, future default privileges, unsafe-role/schema rejection, exact secret version requests, redacted failures and reference-only output. No cloud readiness or live credential injection is inferred from these results.
